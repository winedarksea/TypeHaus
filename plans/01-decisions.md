| 55 | Humidity is its own axis | **2026-08-18.** A room that is *run* wet gets `Room.humidity_class` (`NORMAL` / `WET` / `HUMID`) plus optional `design_relative_humidity` / `design_temperature_f`, not a new `Occupancy` member. Occupancy describes *use* — the plant room genuinely is `LIVING` and the sauna genuinely is `BATHROOM` — and a separate axis is the only shape that lets showers, sauna and plant room share one set of rules. `WET` is intermittent (dries between sessions), `HUMID` continuous (no drying window, so no forgiveness). The axis is what scopes `building_science.condensation` **per (wall, interior room)** instead of per assembly tag: the same stack is a different question at 70 % RH than at 35 %, and before this the walk analysed every assembly at the whole-house figure and read `assembly.default_lining`, so a 70 %-RH room would have been checked at 35 %. | 56 | The humid side is a wall *type* | **2026-08-18.** RM-S-PLANT's liner follows the sauna precedent exactly — `PLANT_EXT_2X6_HUMID` / `PLANT_INT_2X6_BRG_HUMID` / `PLANT_INT_2X4_HUMID`, not a `Room.wall_lining` override — for three reasons that each decide it alone: the liner changes the wall's thickness (a lining override may not), an asymmetric wall needs `interior_room` to name the face it lands on, and only a type is a thing the condensation walk and #55's rules can see. **The panel is not the vapour barrier.** No PVC or FRP maker publishes a perm rating, so the control layer is a separate sealed membrane behind the panel, and the model says so the only honest way: `pvc-panel` and `vinyl-sheet` carry no permeance at all (per #46's convention) and the membrane carries a *specification* value with its basis in `source=`. The consequence is deliberate — `building_science.condensation` reports UNKNOWN on those assemblies, naming the panel, and `humid_room_liner` is the rule that answers. Interior walls align on the stud centreline (`face("stud-ext", offset=…)`, the W-B-CS idiom) so the liner grows into the humid room and the bearing grid does not move (#43). **Later the same day the sauna's own fourth face followed the same rule**: `W-B-S2`'s south side was bare concrete because every non-structural layer of `CATLIN_BASEMENT_12_GARDEN` sits *outboard* of the pour, so it took `SAUNA_LINER_ON_BASEMENT_12_GARDEN` — a wall type, not a lining override, for the same three reasons. A concrete-backed variant needs **no** alignment offset: it stays on `face("concrete-ext")` because on that wall the concrete's outboard face *is* the datum, so the pour does not move and only the liner grows inward. W-B-CS's `offset=inch(-6)` exists solely to re-centre its concrete on the 18' bearing grid, which is a different problem. And a liner on a foundation wall states its own ceiling: the three liner layers carry a `LayerExtent` off `WALL_TOP` so a 7'-6" room does not bill 9'-0" of basswood. |

## Naming & rename-ease strategy

Name is now locked (#9: `Type:Haus` / PyPI `typehaus` / domain `type-haus.com` / CLI `haus`),
but the codebase stays engineered for a cheap rename if one is ever needed:

- **One import root:** all Python code lives under `packages/engine/src/typehaus/`. No
  sub-package embeds the brand (they're `typehaus.model`, `typehaus.emit`, …). A rename =
  rename one directory + one `pyproject.toml` `name` + find/replace `typehaus` imports.
- **CLI is `haus`**, not `typehaus` — user muscle memory survives a rename.
- **Brand strings centralized:** `typehaus/_meta.py` exposes `PROJECT_NAME`, `PROJECT_URL`,
  `IFC_APP_NAME` (used in IFC headers, pset prefixes `Pset_TH_*` — keep the pset prefix short
  and brand-agnostic: use `Pset_TH_Source` but define the prefix as a constant in `_meta.py`).
- **UI:** brand only in one `branding.ts` constant file.
- Include a `docs/RENAME.md` checklist (pyproject name, src dir, npm package name, GitHub
  repo, docs site, `_meta.py`, `branding.ts`).

## Reviewer items considered and rejected/deferred (so they don't resurface unexamined)

- **Loro / CRDT sync** — rejected again (decision #4's rationale is unchanged): the round-trip
  counterparty is an architect's tool rewriting files wholesale, invisible to any CRDT; local
  concurrency is handled by #30's preconditions + locking; multi-user collaboration is git's
  job. Revisit only if real-time co-editing becomes a goal, which it is not (→ 00 §Non-goals).
- **"Reframe round-trip as controlled change review"** — already the design: (→ 20 §Diff) *is*
  a change review (semantic diff → per-change accept/reject via `/import-review` → decision log
  in the handoff bundle). No change needed.
- **`library.lock`** — deferred, not rejected: while `library/` ships inside the engine
  package, the `requires_engine` pin (#31) transitively pins every library item. A lockfile
  becomes necessary exactly when library items are distributed/versioned independently of
  engine releases — add it then, not before.
- **Built-in regional cost data** — rejected (#28): guaranteed wrong somewhere, high
  maintenance, and it would launder guesses into authority. User-supplied `prices.toml` gives
  the same UI with honest provenance.
- **Persistent constraint solver for dimensions** — rejected in favor of the anchor-pin scheme
  (#26): no solver in the < 2 s edit loop, no over/under-constrained failure modes, every
  dimension edit stays one journaled op. Revisit only if real usage shows anchor pins are
  insufficient.
- **Guardrail / handrail code enforcement** — deferred as a *check*, not built as a modeled
  system. Guard height, baluster spacing, and handrail graspability (R312 / R311.7.8) are
  finish-stage decisions easily resolved on site; a design-time code gate here would mostly
  generate noise and frustrate users chasing a permit-plan bar that finishing will settle
  anyway. Guards/rails can be drawn as ordinary `Annotation` symbols where a drawing calls for
